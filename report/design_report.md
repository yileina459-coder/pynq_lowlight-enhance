# 设计报告：低延迟视觉增强终端（PYNQ-Z2）

> 参赛方向：2026 全国大学生嵌入式芯片与系统设计竞赛 · FPGA 创新设计赛道 · AMD 自主选题赛道（初级组）
> 器件：Zynq-7000 XC7Z020（PYNQ-Z2）　工具：Vivado / Vitis HLS 2026.1
> 提交截止 2026-11-04；证据分两条独立链路：DMA 通路的逐位比对 + HDMI 通路的采集卡截图。
> 本报告中的所有数字都来自仓库内的脚本与日志，路径随文给出，可逐条复核；
> 全局口径见 [`docs/facts.md`](../docs/facts.md)。

## 1. 选题背景与创新点

### 1.1 要解决的问题

**主问题（应用侧）**：低照度条件下的图像观察——夜间或弱光监控、暗光环境下的巡检与取证、
车载夜视辅助、工业与显微成像的弱光画面。这类场景的困难不是分辨率，而是画面偏暗、反差不足；
通用手机/PC 方案从采集到显示通常有 100~300 ms 延迟，移动观察时会出现画面迟滞与拖影，
长时间使用容易疲劳。这类设备的核心指标不是帧率，而是延迟。本作品因此把增强链放进像素流
（不经过帧缓冲），把**处理延迟**压到 21 个像素时钟（147 ns，约为 720p60 一行的 1%）；
帧源由 PS 预载、VDMA 送入，代价是放弃帧级后处理（降噪、稳像等）。本板 HDMI 输出只支持
640×480、输入又不支持该模式，直通链路受硬件限制没有打通——所以这里测到的是 **PL 内部延迟**，
不是端到端延迟。

**工程问题**：视频处理算法的硬件加速常被当作"把算子写进 FPGA 就快了"，但真正决定作品价值的三个问题是：
**结果对不对、比软件快多少、别人能不能复现**。本项目围绕这三点组织：

- 每个算子都有**独立的软件黄金模型**，硬件输出与之做 **0 容差逐像素比对**；
- 同一算法同时给出 **PS 纯软件实现**与 **PL 硬件实现**，用同一套输入、同一套测量脚本对比；
- 全部流程脚本化（HLS 工程、块设计、位流、上板测试），一条命令可从零重建。

### 1.2 创新点

| 创新点 | 具体做法 | 为什么有价值 |
| --- | --- | --- |
| 零帧缓存流水线 | 增强链全在像素流中完成（局部对比 → 色调曲线 → 二值/反色 → 分屏），不落 DDR | 处理延迟 21 个像素时钟（147 ns），而不是一帧；这是低照度观察场景的**核心指标** |
| 流式算子内核 | 行缓冲 + 3 抽头移位寄存器，II=1，`ap_ctrl_none`，无 AXI-Lite 依赖即可插在视频流中间 | 流水线深度 21 拍；可直接嵌入 HDMI 通路 |
| 边界策略显式化 | 水平复制、垂直用上一帧行，写进头文件注释、测试台与 Python 参考 | 这是"硬件和软件对不上"的头号原因，显式定义后可以要求 0 误差 |
| 双路验证 | DMA 版（可回读、可数字验证）+ HDMI 版（持续出图）共用同一内核 | 没有显示器也能证明硬件正确；有显示器时又能在真实像素流上演示 |
| 可复用工具链 | 五个通用 PYNQ Skill（overlay 离线校验、逐位比对、性能数据入库、DMA 封装、踩坑清单） | 换题目、换板卡仍可用，符合赛题"通用 PYNQ Skill"加分项 |

## 2. 设计原理与功能框图

### 2.1 系统框图

```text
 PS 预载图像/视频 ─► DDR ─► AXI VDMA MM2S ─► stamp_in ─► enhance ─► stamp_out
                                                              │
                                                              ▼
 HDMI OUT ◄─ rgb2dvi ◄─ v_axi4s_vid_out ◄─ sof_gen ◄─ pixel_unpack

 PS (ARM Cortex-A9)：Jupyter / Python ── AXI-Lite / GPIO ── 59 bit 配置 ──► cfg_bram
```

两条数据通路共用同一个算子 IP：

| 通路 | 结构 | 用途 |
| --- | --- | --- |
| DMA 版 | PS ↔ DDR ↔ AXI DMA ↔ 算子 | 数字验证（与黄金参考逐位比对）、便于自动化测试 |
| HDMI 版 | PS → DDR → VDMA → 算子 → HDMI OUT | 在真实像素流上持续出图（640×480），提供视觉与延迟证据 |

### 2.2 算子内核结构（以 Sobel 为例）

> `enhance` 不是卷积核，它是逐像素链（局部对比需要 3×3 邻域，其余是逐点运算），结构见 §5.2；
> 这里用 Sobel 说明"行缓冲 + 抽头 + II=1"的通用做法。

```text
 像素流 ──► 亮度 Y=(77R+150G+29B)>>8 ──► 行缓冲×3（轮转）
                                              │
                          ┌───────────────────┴───────────────────┐
                          │  每行 3 抽头移位寄存器 → 3×3 窗口        │
                          │  Gx = 右列 − 左列,  Gy = 下行 − 上行      │
                          │  M  = |Gx| + |Gy|，饱和到 0..255         │
                          └───────────────────┬───────────────────┘
                                              ▼
                                     {M,M,M} 复制到 RGB
```

关键设计决策：

1. **三个行缓冲轮转 + 每行移位寄存器**，使每个像素对每个行缓冲只做 1 次读、1 次写，
   正好落在真双口 BRAM 的能力内，这是 II=1 能成立的原因；
2. **整数亮度与整数梯度**，不使用浮点，保证硬件与软件参考**逐位一致**；
3. **`ap_ctrl_none`**：无 start/done 握手，数据到即处理，适合插在视频流中间；
   行边界由 `TLAST` 识别，因此不需要在运行时配置分辨率。

## 3. 软硬件划分依据与接口设计

### 3.1 划分依据

| 功能 | 放在 | 理由 |
| --- | --- | --- |
| 视频时序、颜色空间转换、像素打包 | PL（PYNQ 官方 IP） | 需要与像素时钟严格同步 |
| 卷积算子 | PL（自研 HLS） | 每像素固定算术，适合流水；PS 上逐像素循环慢两个数量级 |
| 参数配置、状态监控、UI | PS（Python/Jupyter） | 变化慢、需要交互，放软件更灵活 |
| 黄金参考与比对 | PS / 主机 | 需要浮点与丰富库，且要独立于硬件实现 |

### 3.2 接口定义

**算子 IP（AXI4-Stream）**

| 端口 | 位宽 | 语义 |
| --- | --- | --- |
| `s_in_tdata` | 32 | 低 24 位为 `{R,G,B}`，高 8 位透传（alpha/控制） |
| `s_in_tlast` | 1 | 行尾 |
| `s_in_tkeep/tstrb/tuser/tid/tdest` | — | 原样透传 |
| `s_out_*` | 同上 | 每输入一拍输出一拍 |
| `ap_clk` / `ap_rst_n` | — | 与视频通路同域（`clk_142M`） |

**DMA 版寄存器**：仅 AXI DMA 自身寄存器（`0x41E00000–0x41E0FFFF`），算子无 AXI-Lite。

**HDMI 版配置接口**：59 bit 拆成两个字，经 AXI GPIO 写进 `cfg_bram`（XPM 真双口：写侧 100 MHz、
读侧 142.857 MHz）；内核每像素读一次。因此改参数不需要复位内核，也不中断像素流（§5.2）。
帧起始（SOF）由 `sof_gen` 按 480 行 TLAST 生成，接在 `pixel_unpack → v_axi4s_vid_out` 之间。

## 4. 优化过程与前后对比

### 4.1 已完成的三次优化

| 轮次 | 问题 | 措施 | 结果 |
| --- | --- | --- | --- |
| 1 | 24 位像素流无法直接接 AXI DMA（DMA 只搬 32 位字，4:3 位宽转换不可实现） | 把像素位宽做成 `SOBEL_PIX_W` 宏，核只取低 24 位、其余透传 | 同一份源码同时服务 DMA（32）与 HDMI（24）两条通路 |
| 2 | 10 ns 约束下估计 Fmax 141.9 MHz，低于视频通路 142.86 MHz | 把约束改为 7 ns 重新综合 | 估计 Fmax **194.59 MHz**，II 仍为 1 |
| 3 | 高斯核"先行后列"两遍实现导致中间结果被 8 位字段截断 | 改为一次 9 抽头求和、12 位累加器，最后统一 `>>4` | C 仿真从 FAIL 变为 0 误差 |

### 4.2 资源与时序（HLS 综合，`xc7z020clg400-1`，7 ns）

| 算子 | BRAM | DSP | FF | LUT | II | 估计 Fmax |
| --- | --- | --- | --- | --- | --- | --- |
| **enhance（主算子）** | 3（1%） | 2 | 2168（2%） | 1659（3%） | 1 | 194.59 MHz |
| Sobel | 3（1%） | 2 | 583 | 809（1%） | 1 | 194.59 MHz |
| Gaussian | 9（3%） | 0 | 1021 | 986（1%） | 1 | 194.59 MHz |

完整实现（DMA overlay，100 MHz）：LUT 4027（7.6%）、FF 5645（5.3%）、BRAM 3.5（2.5%）、DSP 3（1.4%），
**WNS +3.086 ns**（`build/overlay_dma/out/timing_impl.rpt`）。

完整实现（HDMI overlay = PYNQ base overlay + Sobel，142.857 MHz）：LUT 33098（62.2%）、FF 46563（43.8%）、BRAM 80.5（57.5%）、DSP 21（9.6%），**WNS +0.207 ns**、0 个失败端点（`board/hdmi_stream/timing_impl.rpt`）。资源占用主要来自 base overlay 的 MicroBlaze、音频、Arduino/Pmod/树莓派 IO 子系统，自研 Sobel 核本身只占约 1%——这组数字说明“把算子插进现成框架”的代价主要在框架，而不在算子。

### 4.3 PS 与 PL 对比（板上实测）

同一块 PYNQ-Z2、同一张 1280×720 测试图、同一个 Sobel 算法（同一亮度公式与边界策略）：

| 指标 | PS（ARM Cortex-A9 + numpy） | PL 逐行传输 | PL **整帧传输**（最终） |
| --- | --- | --- | --- |
| 每帧时间 | 3108.4 ms | 659.1 ms（4.72×） | **15.8 ms（196.7×）** |
| 帧率 | 0.320 fps | 1.516 fps（4.74×） | **63.45 fps（198.3×）** |
| 像素吞吐 | 0.30 Mpixel/s | 1.397 Mpixel/s（4.66×） | **58.47 Mpixel/s（194.9×）** |

数据来源：`board/dma_sobel/metrics_board.csv`，原始日志 `board/dma_sobel/metrics.csv`，
表格由 `sim/perf/make_comparison.py` 生成（`report/comparison.md`）。

两点必须说明，否则这组数字会被误读：

1. **逐行传输的 659 ms 里绝大部分不是算子时间**，而是软件开销：每帧 720 次核启动 +
   1440 次 DMA 传输 + 轮询，每次都要走 Python。改成**整帧一次传输**（1 次核启动 +
   2 次传输）后降到 **15.8 ms**，提升 41 倍——这一步同时需要把 DMA 的传输长度寄存器
   从 14 位放宽到 23 位（默认上限只有 16 KB），并让核按 `line_width` 自己数行边界；
2. 两边的输出**逐像素完全一致**（`skill/golden_compare` 比对 2764800 个通道，0 不一致），
   也就是这 196.7× 是在「结果完全相同」的前提下取得的，不是用精度换速度。

主机（x86 笔记本）上的 numpy 只要 40.7 ms/帧，比板上的 PL 还快——这条也如实记下来：
本作品对比的是「同一块嵌入式板卡上，用 ARM 做还是用 PL 做」，不是「跟桌面 CPU 比」。

### 5.1 真机 HDMI 演示（2026-10-21/22；历史方案，已由 §5.2 取代）

> 这一节记录的是"复位内核 + 重建输出链路"的那一版：当时的 7 档循环、切预设当帧会黑一下。
> 现在的交付方案是 §5.2 的 BRAM 配置：10 档、不复位、不中断像素流。保留本节是因为
> "为什么不是 HDMI 进 → HDMI 出"的硬件结论仍然有效。

**数据通路**

```
PS 写一帧到 DDR → VDMA MM2S → stamp_in → enhance → stamp_out
               → pixel_unpack → v_axi4s_vid_out → rgb2dvi → HDMI OUT → 采集卡 → OBS
```

内核位于真实像素通路上，PS 只负责送帧和改配置；整条链路没有帧缓冲参与运算。

**为什么不是"HDMI 进 → HDMI 出"**

两条实测的硬件限制把它排除了：

1. **这块 PYNQ-Z2 的 HDMI 输出只能驱动 640×480**。判据是 `writeframe()` 是否返回
   （它只在 VDMA 完成一次帧传输后才返回，因此与采集卡无关）：

   | 输出模式 | 像素时钟 | `writeframe` | 采集卡 |
   | --- | --- | --- | --- |
   | 640×480 | 25.175 MHz | 立即返回 | 有画面 |
   | 800×600 | 40 MHz | 阻塞 | 无信号 |
   | 1280×720 | 74.25 MHz | 阻塞 | 无信号 |
   | 1920×1080 | 148.5 MHz | 阻塞 | 无信号 |

   用**原厂 `base.bit`** 测同样结果，所以这是板子的物理上限（PYNQ-Z2 的两个 HDMI 口
   无缓冲、直连 PL），不是本次改动引入的。

2. **HDMI 输入无法工作在 640×480**：`dvi2rgb` 的 `kClkRange` 只接受 1/2/3
   （设 5 会被 IP 拒绝），而 25.175 MHz 需要 5 档才能让 VCO 落在 600–1200 MHz。

两者叠加使"输入输出同分辨率"无解，因此帧源改为 VDMA。

**运行期切换预设：HLS 的一个隐蔽陷阱**

第一版切换预设时画面几乎不变。查生成 RTL 发现，HLS 把**循环不变量输入**提到流水线
prologue 里锁存：

```verilog
reg [0:0] binarize_read_reg_1446;
1872: binarize_read_reg_1446 <= binarize;         // 只采一次
2312: y3 = (binarize_read_reg_1446 == 1'b1) ? …  // 之后永远用旧值
```

而 `clarity` 是组合直连的。逐项核对结果：`clarity/gain_lo/gain_hi` 实时生效，
`knee/thresh/binarize/invert/mono/split_x` 在开机时冻结。根因是内核为
`ap_ctrl_none` 自由运行，prologue 只执行一次。

修法分两层：

1. `enh_rst_bridge` 让 PS 用配置字空闲位 `cfg_hi[31]` 复位内核，prologue 重新采样；
   写配置的顺序必须是"参数就位 → 断言复位 → 释放"。
2. 复位**释放**必须同步到内核时钟域（异步断言、两级同步释放），否则内核可能带着
   错乱的 line buffer 指针退出复位——板上表现为**某些预设持续闪烁**，而不是稳定花屏一帧。

**第三个问题：切预设后画面在"图像 ↔ 黑"之间交替**（已彻底解决，见 5.2）

复位内核会让 AXI-Stream 中断，`v_axi4s_vid_out` 随之欠载，采集卡只能自行重新锁定——
这个过程在屏幕上就是图像与近黑帧交替。排查中先后用客观判据排除了若干假设：

| 假设 | 判据 |
| --- | --- |
| 帧缓冲里有未写入的黑帧 | 读回 4 块缓冲，`mean=131.5 / max=235`，全为正常图像 → 排除 |
| 输出链路本身不稳 | 静态灰面 85 秒，延迟恒定 21 拍 → 排除 |
| 采集卡/缩放锯齿 | 采集源改 1:1、640×480 后仍闪 → 排除 |
| 写 DDR 造成撕裂 | 只写一帧仍闪 → 排除 |

修法是**不指望采集卡自己恢复，而是主动重建输出链路**：

```python
write_preset(cfg, name)          # 复位内核，prologue 重新采样 9 个配置位
out.stop(); out.configure(mode); out.start()
for _ in range(4):               # 填满 4 块帧缓冲，避免任何黑帧
    f = out.newframe(); f[:] = image; out.writeframe(f)
```

**板上实测**

| 项目 | 数值 |
| --- | --- |
| 输出分辨率 | 640×480 @60 |
| 每帧写入耗时 | 6.4 ms（VDMA 持续消费） |
| 流水线延迟 | **21 拍**（HLS `Depth = 21`）；片上单次测量 21–25 拍，含启动偏斜 |
| 预设切换 | 15 次切换各带一次输出重建，延迟全程 21 拍；切换瞬间闪一下、之后稳定 |
| 证据 | `board/hdmi_stream_enhance/evidence/`：原始、垂直分屏、硬阈值、过锐四态 |
| 演示主脚本 | 当时的 `board/hdmi_stream_enhance/archive/hdmi_preset_only.py`（现归档） |

**判读说明**：截图按"画面里能看到什么"命名（垂直分界 / 硬阈值 / 过锐 / 原始），
而不是按 PC 时间戳去对档名——板子时钟与 PC 不同步，硬对时间会引入错误结论。

### 5.2 把配置搬进存储器，切换不再闪

5.1 里的修法是"复位内核 → 重建输出链路"，代价是切换瞬间黑一下。根因其实在更上游：
HLS 把 9 个配置参数当作循环不变量锁进了流水线 prologue，而自由运行内核只跑一次
prologue，所以改参数**必须**复位。

**改法**：新增 `enhance_stream_cfg`，配置从一块 64 位存储器按像素读取。内存读无法被提到
循环外，参数因此实时生效，切预设退化成一次寄存器写。

**一个不显然的细节**：读地址必须是运行期值。第一版读 `cfg[0]`，HLS 证明下标是常量后把
数组折成普通输入端口，标志位又被锁存（`binarize_reg_1458 <= cfg[40]`）。让下标依赖
`col` 之后才生成真正的存储器端口，生成 RTL 变成
`binarize_reg_1575 <= cfg_Dout_A[40]`，每周期重采样。综合仍为 **II=1、194.59 MHz**。

**存储器实现**：`src/rtl/cfg_bram/cfg_bram.v`，两字、真双口、写侧 100 MHz / 读侧
142.857 MHz。必须用 `xpm_memory_tdpram` 显式例化——推断出来的触发器版本把跨时钟变成
受时序检查的路径（**WNS −1.393 ns，59 个失败端点**），换成 XPM 后 0 个失败端点
（那一版 +0.289 ns；交付位流加入 SOF 后为 **+0.206 ns**，见 §4.2）。

**上板实测**

| 项目 | 数值 |
| --- | --- |
| 切换期间写帧次数 | **741**（150 秒，25 次切换） |
| 单帧写入耗时 | min 2.1 / median 2.2 / max 17.1 ms |
| 超过 60 ms 的卡顿 | **0** |
| 流水线延迟 | 全程 **21** 拍（同一轮内恒定） |

判据的构造方式本身是关键：`writeframe()` 只在 VDMA 完成一帧后才返回，所以**任何一次流
中断都会表现为一次长写**。0 次卡顿即"没有中断"，也就没有黑屏——不必靠肉眼判断。

**自选图片输入**：`tools/make_frame.py` 在电脑侧把任意图片转成 640×480×3 裸 RGB
（letterbox 或 crop），`hdmi_show_image.py` 在板上显示并可轮播预设；
`tools/check_frame.py` 校验两侧的测试图**逐字节一致**、通道为 R,G,B 顺序，避免红蓝互换
这类能一路带到答辩现场的错误。Jupyter 面板也加了上传控件。

**输出画面偏移：相位属于这一路像素流，交付流程每次启动标定**

纯流式流水线延迟像素却不延迟时基，`v_axi4s_vid_out` 按固定行时序开窗，画面会整体水平环绕。
该核依赖 AXI4-Stream 的 TUSER0 作为帧起始（SOF）把输入帧对齐到时序发生器（Xilinx PG044）；
本设计的 TUSER 来自 VDMA 且恒为 0，输出核只能自由跑。交付位流里加了 `sof_gen`：用
"每帧 480 行 TLAST"生成 SOF，把帧边界锚定到 480 行计数上。但计数器从复位开始数，
**第一个帧边界是流启动后遇到的第一条 480 行边界**，所以相位仍取决于启动时刻，只是落在
亚行范围、并且在一路流内稳定。

2026-10-24 实测（同一路像素流）：`roll=0` 时画面从源图第 **216.8** 列开始；写 `roll=218` 后
行首对齐，真实书页与推送 PNG 的互相关峰值 `dx=0, dy≈−1`，残差 **0–1 px**。同一路流内换图、
换挡位、0.2 s 重推都不变；只有重启像素流才变。历史上同一份位流测到的 0 / 45 / 89 px（以及
一次 0.3 px）都来自**不同的流**；早期"每帧随机相位"的结论已确认是测量缺陷（截图抓错了
OBS 窗口），完整记录见 [`docs/output_offset.md`](../docs/output_offset.md)。

因此交付流程是"**启动后测一次、写补偿、复测残差**"：`tools\board\fix_offset.ps1`，
`ensure_demo.ps1` 在拉起演示后自动调用；视频上传不再清零标定值（`play_video.ps1` 的
`-Roll` 默认 `-1`）。位流层面的根治（真实帧边界 SOF / 接出 VDMA 的 TUSER）需要重建位流，
本次未做。

**预设与亮度（补充 §5.2，板上实测）**

内核的色调曲线是两段线性（`knee` 以下乘 `gain_lo`、以上乘 `gain_hi`），`clarity` 做局部对比
增强。同一张暗图（整幅 ×0.28）在板上实测平均亮度：`pass` 29 → `bright` 96（3.5×）→
`document` 100（4.0×）→ `night` 104（4.5×），高光截断均在 0.2% 以下。此前"处理前后没差别"
的原因是上传路径固定写 `pass`（恒等），而不是硬件没有能力。

`tools/preview_enhance.py` 用同一套定点运算离线复现内核，可按图片自动挑选预设，
窗口的「预览效果」即调用它，因此预览结果与板上一致。

## 9. 尚未完成与已知限制

**HDMI 通路已达到的状态**（推导与逐条证据见 `docs/hdmi_status.md`）

| 项目 | 状态 |
| --- | --- |
| 输出画面 | ✅ 640×480 @60，采集卡实测稳定 |
| 内核在像素通路上 | ✅ 延迟 **21 个像素时钟 = 147 ns**（两道时间戳夹出来） |
| 运行期切换预设 | ✅ **10 档**，不复位、不重建输出链路（741 次写帧 0 次卡顿） |
| 画面偏移 | ✅ 每次启动后自动标定（本次 218），残差 **0–1 px**；位流层面未根治 |
| 逐位正确性 | ✅ DMA 通路 8 档（验证参数表）各 **0/2764800** 通道不一致 |

**已知限制（都是实测结论，不是推测）**

1. **HDMI 只能 640×480，且无法直通。** 这块 PYNQ-Z2 的 HDMI 输出只有 640×480 能驱动
   （800×600 / 720p / 1080p 下 VDMA 一帧都不消费、不产生 TMDS，**原厂 `base.bit` 同样如此**，
   HDMI 口无缓冲直连 PL）；而 HDMI 输入又无法工作在 640×480（`dvi2rgb` 的 `kClkRange`
   只接受 1/2/3，25.175 MHz 需要 5 档才能让 VCO 落在 600–1200 MHz）。两者叠加使
   "输入输出同分辨率"无解，因此帧源改为 VDMA。
2. ~~换预设的当帧会闪一下~~ **已解决（§5.2）**：配置改为每像素从 BRAM 读取，
   切预设只需一次寄存器写，实测 741 次写帧 0 次卡顿、延迟恒定 21 拍。
3. **画面偏移需要每次启动标定。** 相位属于这一路像素流（本次 216.8 px → `roll=218`），
   SOF 生成器只把它收敛到亚行范围，没有钉死为 0；位流层面的根治需要重建位流（§5.2）。
4. **HDMI 通路无法用 `readframe()` 取帧。** VDMA 环回被切断，数据只在 PL 内流动，
   因此数字验证走 DMA 通路（`board/enhance_dma/`），HDMI 通路只提供视觉与延迟证据。
5. **功耗未测。** PYNQ-Z2 无板载功率计，报告中没有功耗数据，也没有估算值。
6. **算子三路并行未接进同一个 overlay。** Sobel / Gaussian / Sharpen 各自验证充分，
   但 `axis_mux3` 只做到综合级验证（本机 `xsim` 启动即崩），且时序余量不足以再叠三路。
7. **DMA 逐行传输慢（659 ms/帧）。** 那是刻意保留的对照配置（`--per-row`），
   用于说明"每行一次传输的固定开销"会让帧率崩掉；默认路径是整帧传输 15.8 ms。
8. **时间约束**：提交截止 2026-11-04，团队自设止损 2026-11-01。

**交付形态**：HDMI 增强通路（640×480@60，21 拍 = 147 ns，10 档运行期可切，偏移每次启动标定）
+ DMA 逐位验证通路（8 档参数表 0 误差、15.6 ms/帧；Sobel 相对 PS 196.7×）共用同一份 HLS 源码，
两条通路的证据互相独立。
