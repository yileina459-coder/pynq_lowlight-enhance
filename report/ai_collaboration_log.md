## 2026-10-18 / P0 环境基线

### 交互 1：让模型通读全部资料

**提示词**
> 我参加这一届FPGA的AMD赛道的自选赛题，一些相关内容全在这个文件夹中。你先全部浏览一遍

**模型产出**
- 遍历仓库（14 个文件 + 2 份 PDF），指出 `src/sim/build/board/data/skill/report` 全为空壳
- 发现两份 PDF 无法直接读（目录里没有 PDF 解析库、没有 pdftotext），自行写了一个
  PDF 文本提取脚本（`.tmp/pdftext.py`），提取出选题指南 25 页与选题笔记 2 页全文

- 指出仓库里 `xlicdiag.rpt` 显示许可异常（`No SERVER lines in license file`），列为风险

**错误与纠正（第一次）**
第一版提取器把中文输出成一堆乱码。原因是：只支持了 `bfrange` 的 `<lo> <hi> <dst>` 形式，
而这两份 PDF 用了 `[<d1> <d2>]` 数组形式；另外把 `(en-US)` 这类 `/Lang` 属性当成正文抽了出来。
修正后仍有一处乱码：PowerShell 的重定向把 Python 的 UTF-8 输出写成了 UTF-16，
读回时被当成单字节文本，还产生 18995 个 NUL 字符。改为**由 Python 自己写文件**（`open(..., encoding='utf-8')`）后正常。

**人工判断**
- 确认了"初级组"报名身份与 PYNQ-Z2 的合规性
- 确认了分辨率先做 720p（PYNQ-Z2  HDMI 端口的官方上限）

### 交互 2：开始实际开发

**提示词**
> 我需要你逐步辅助我完成这个项目。

**模型产出**
- 自动侦察环境：找到 Vivado/Vitis 装在 `D:\AMD_vivado_vitis\2026.1`
- 发现 `vitis_hls` 命令不存在，写包装脚本 `tools/env/vitis_hls.bat`
- 跑通两个冒烟工程并入库：`build/smoke/vivado`（综合）、`build/smoke/hls`（C 仿真 + 综合 + 导出 IP）
- 落文档 `docs/env.md`、`docs/roadmap.md`

**错误与纠正（第二次）**
1. 包装脚本第一版只调了 Vitis 的 `setupEnv.bat`，`export_design` 报

## 2026-10-18 / P2 第一个 HLS 算子（Sobel）

**提示词**
> 我就只有一个笔记本电脑 / 我是零基础，你看着来，可以上github或者其他网站搜索类似开源项目作为参考

**模型产出**
- 写流式 Sobel 核：`src/hls/sobel/{sobel.hpp,sobel.cpp}`
- 写独立的 C++ 黄金模型测试台：`src/hls/sobel/tb_sobel.cpp`（推 3 帧，检查帧边界上的行缓冲轮转）
- 写 Python 黄金参考与 bit-exact 比对：`sim/sobel/golden_sobel.py`
- 生成 720p 测试图与参考输出：`data/images/test_720p.png`、`data/reference/sobel_720p.png`
- 结果：C 仿真 9216 拍 0 误差；II=1；Fmax 141.9 MHz；BRAM 3 / DSP 2 / FF 583 / LUT 809
- 检索并读了三份同类开源项目，写进 `docs/references.md`

**错误与纠正（第三次）**
1. `ap_int` 的三元表达式 `gx < 0 ? -gx : gx` 编译报
   `conditional expression is ambiguous; ap_int<17> can be converted to ap_int<16> and vice versa`
   ——取负会让位宽加 1。修正：先算 `neg_gx`/`neg_gy` 两个同宽临时量再选择。
2. 第一版像素接口写死 24 bit，而 AXI DMA 只能搬 32 bit 字，会导致中间要塞一个
   4:3 的位宽转换器（不可实现）。修正：把 `SOBEL_PIX_W` 做成可配置宏，
   DMA 路线用 32、HDMI 路线用 24，核只取低 24 位、其余位透传。

**人工判断**
- 边界策略（水平复制、垂直用上一帧行）由模型提出、队员确认：它直接决定"能否和软件参考逐位对上"
- 比对标准定为 **bit-exact（0 个通道不一致）**，不接受 PSNR 阈值

## 2026-10-18 / P3a DMA 版 overlay（不需要显示器的验证路线）

### 交互：继续自主推进

**提示词**
> （目标轮次自动继续）继续完成项目

**模型产出**
- `build/overlay_dma/`：一条 `build.bat` 走完 解包 HLS IP → 建块设计（PS + AXI DMA + sobel_stream）→
  实现 → 出位流 → 从 XSA 拆出 `sobel_dma.bit` / `sobel_dma.hwh`
- `board/dma_sobel/`：上板脚本 `sobel_dma.py`（逐行 DMA）、`demo.ipynb`、README
- `sim/sobel/test_sobel_dma_offline.py`：用 numpy 假 DMA 复现核行为，**在主机侧先验证上板脚本**
- `skill/overlay_check/`：上板前离线校验 `.hwh`

**实测结果**（`build/overlay_dma/out/`）：WNS **+3.086 ns**（100 MHz 下满足时序）、
LUT 4027（7.57%）、FF 5645（5.31%）、BRAM 3.5（2.5%）、DSP 3（1.36%）。

**错误与纠正（第四次～第八次，全部是工具链细节，但每一条都能卡住一天）**

1. `CONFIG.c_m_axis_s2mm_tdata_width` 不存在（CRITICAL WARNING: Parameter does not exist）。
   AXI DMA 的 S2MM 流位宽参数叫 `c_s_axis_s2mm_tdata_width`（slave 侧）。
   修正方式：先用一个 60 行的探测脚本把 IP 的合法参数全打印出来，再改，而不是靠猜。

2. `set_property offset ... [get_bd_addr_segs ...]` 报 `Cannot change read-only property 'offset'`。
   修正：删掉手工地址，交给 `assign_bd_address` 自动分配——PYNQ 是从 `.hwh` 读真实地址的，
   手工指定只会增加冲突风险。

3. `validate_bd_design` 失败：`/ps7/M_AXI_GP0_ACLK` 与 `/ps7/S_AXI_HP0_ACLK` 没有时钟。
   PS 的 AXI 端口也要显式接 `FCLK_CLK0`，不只是从设备要接。

4. `Expand-Archive` 拒绝解压 `.xsa`（只认 `.zip`）。XSA 本质是 zip，改用
   `System.IO.Compression.ZipFile::ExtractToDirectory`。

5. `.hwh` 解析失败：2026.1 的属性是大写 `INSTANCE`/`MODTYPE`，时钟频率放在
   `<PORT CLKFREQUENCY="...">` 而不是 `<CLOCK>` 元素。第一版解析器按旧格式写，输出全空。
   修正后兼容两种写法——这也是 `skill/overlay_check` 要打印原始清单的原因。

6. PYNQ 版本差异：`ol.axi_dma_0` 在某些版本是 `DefaultIP`（没有 `sendchannel`）。
   `find_dma()` 改成"拿不到 DMA 驱动就用 `pynq.lib.dma.DMA` 包一层"，避免版本差异直接崩。

**人工判断**
- 主路线仍是 HDMI 流式；DMA 版是"没有显示器也能证明硬件正确"的过渡验证
- DMA 按行传输的帧率**不代表**最终性能，只用于功能验证；真实性能在 P3b 测

## 2026-10-18 / P3a 收尾与 P3b 预研

**模型产出**
- DMA overlay 位流构建完成并入库（`board/dma_sobel/sobel_dma.bit`）：WNS **+3.086 ns**、
  LUT 4027（7.6%）、FF 5645（5.3%）、BRAM 3.5（2.5%）、DSP 3（1.4%）
- `board/ps_baseline/ps_sobel.py`：PS 侧 numpy 基线（与 PL 同算法同边界），
  主机实测 1280x720 约 **40 ms/帧**（24.6 fps），板上 ARM 会慢数倍
- `docs/p3b_plan.md`：查证 PYNQ v3.1.2 的 base overlay 源码（`boards/Pynq-Z2/base`，
  4448 行、Vivado 2024.1 生成、带版本门禁），给出两条移植路线与风险

**错误与纠正（第九次，这次是操作事故，不是代码 bug）**

在 `.tmp/PYNQ` 里做稀疏检出时，有一条 `cd PYNQ` 因为上一步 clone 失败而没有生效，
命令继续在 `.tmp` 下执行 `git sparse-checkout set boards/Pynq-Z2`。由于 `.tmp` 在仓库内部，
git 向上找到了本仓库的 `.git`，于是**把比赛仓库本身设成了稀疏检出**，
`src/ sim/ build/ skill/ report/ data/` 从工作区消失，并且因为 skip-worktree 位，
`git status` 还显示"干净"——这是最危险的地方：不看文件系统就会误以为没事。

恢复：`git sparse-checkout disable`，所有已提交文件原样回来（因为都已在 0b68874 里）。
复核：`src/hls/sobel/*`、4 MB 位流、测试图都在。

教训（值得写进踩坑清单）：
1. 任何 `git` 子命令在仓库子目录里都可能作用于**整个仓库**，稀疏检出尤其危险；
2. `git status` 显示干净 ≠ 文件都在，稀疏检出会用 skip-worktree 把缺失隐藏掉；
   判断依据应该是 `git ls-files -v`（有 `S` 标记）与文件系统的交叉验证。

## 2026-10-18 / P3b：base overlay 移植到 2026.1（本轮主线）

**提示词**
> （目标轮次自动继续）继续完成项目

**模型产出**
- `build/overlay_hdmi/`：`fetch_pynq.ps1`（按 v3.1.2 稀疏克隆 PYNQ）、
  `patch_base_tcl.py`（3 个补丁）、`insert_sobel.tcl`（切断 VDMA 环回并插入内核）、
  `build.bat`（7 步流水线）
- 关键结论：**PYNQ 官方 base overlay 可以在 Vivado 2026.1 里原样重建**，
  不需要 `upgrade_ip`，也不需要退回 2025.2
- 内核在 7 ns 目标下收敛：估计 Fmax **194.59 MHz**、II=1（视频时钟 142.86 MHz）
- `board/hdmi_stream/`：上板脚本（加载 overlay、配置 HDMI、启动管线）

**错误与纠正（第十次～第十五次）**

1. **版本门禁**：`base.tcl` 头部的 `scripts_vivado_version 2024.1` 会让脚本在 2026.1 里
   直接 `return 1`。改成 2026.1。
2. **PFM_NAME**：脚本末尾 `PFM_NAME {xilinx.com:xd:${overlay_name}:1.0}` 在花括号里，
   Tcl 从不替换变量，2024.1 不校验所以没人发现，2026.1 校验并报
   `PFM_NAME name '${overlay_name}' is not valid`。改成字面量 `base`。
3. **HLS IP 缺失**：base.tcl 列出的 5 个 `xilinx.com:hls:*` IP 在 IP 目录里根本没有
   （仓库只给源码，不给打包好的 zip）。必须先跑 `build_ip.tcl`，而它 `exec vitis_hls`，
   本机 vitis_hls 不在 PATH → 把 `tools/env` 加进 PATH。
4. **PATH 被自己覆盖**：在 `cmd /c "call settings64.bat && set PATH=...;%PATH%"` 里，
   `%PATH%` 在整行解析时就展开了（此时还没 call settings64），结果 Vivado 反而找不到。
   教训：PowerShell 里先设 `$env:PATH`，cmd 里不要再动 PATH。
5. **BOM 让 Tcl 崩溃**：用 PowerShell `Set-Content -Encoding UTF8` 生成的 .tcl 带 BOM，
   Vivado 报 `invalid command name "﻿open_project"`。所有 .tcl 一律用不带 BOM 的方式写。
6. **端口路径猜错**：`get_bd_intf_pins hdmi_in/out_stream` 找不到——实际路径是
   `/video/hdmi_in/out_stream`（`video` 是顶层层次）。用
   `get_bd_intf_pins -hier -filter {NAME =~ "*stream*"}` 一次列全，比猜快。
7. **顺序问题**：`get_property ip_repo_paths [current_project]` 在 `open_project` 之前调用，
   报 `No projects are currently open`。必须先开工程、再设 IP 仓库、然后打开块设计。
8. **两处小坑**：`vitis_hls -f script.tcl` 的 `$argv` 里含有 `-f` 和脚本名，
   解析自定义参数时不能按下标取；`create_bd_cell` 前必须 `update_ip_catalog`，
   否则报 `IP definition not found for VLNV`。

**人工判断**
- 视频通路选择"绕过 VDMA 直通"，换来约一行延迟；代价是 PS 侧不能再 `readframe()`，
  这条取舍写进了 `board/hdmi_stream/README.md`

## 2026-10-18 / P3b 收尾：HDMI overlay 位流建成

**提示词**
> 运行失败的再尝试一次

**结果**
- `board/hdmi_stream/sobel_hdmi.bit`（3.9 MB）+ `sobel_hdmi.hwh`（4.3 MB）构建成功；
- 实现结果：**WNS +0.207 ns**（142.857 MHz，0 个失败端点）；LUT 62.2%、FF 43.8%、
  BRAM 57.5%、DSP 9.6%（框架占大头，Sobel 核约 1%）；
- `.hwh` 通过 `skill/overlay_check`：188 个模块、`sobel_0` 在位、`ap_clk` = 142.857 MHz。

**错误与纠正（第十六次～第十八次）**

1. **OOC 综合的两种失败模式**。base overlay 有近 200 个 IP，默认每个 IP 一个
   out-of-context 综合 run。
   - `-jobs 4` 并发时，多个子进程同时加载 Vivado 的 Tcl app store，报
     `Could not open 'C' for writing` / `tclapp::load_apps failed`；
   - `-jobs 1` 不会撞，但在 32 核机器上串行跑 200 个 run 要几个小时（实测 95 分钟只完成 ~112 个）。
   最终有效做法是**低并发重跑**：已完成的 run 走 IP 缓存，只剩上次失败的 4 个 run，
   `-jobs 2` 大约 15 分钟就收敛到出位流。
2. **"整体综合"这条路没走通**。原本想让所有 IP 走 `synth_checkpoint_mode None`，
   避免逐 IP 的 OOC run；但 `get_ips` 对**块设计内部**的 IP 返回空列表，
   脚本里那句计数打印出来是 `IPs switched to global synthesis: 0`，等于没生效。
   这一点已写进 `build_bitstream.tcl` 的注释，避免下一个人以为它有用。
3. **`axi_vdma` 不是 `axi_dma`**。`skill/overlay_check` 原来只认 AXI DMA，
   对 HDMI overlay（用的是 VDMA）误报 FAIL。修正为两者都算 DMA 通道。

**人工判断**
- 接受 WNS 只有 +0.207 ns 的现实：视频时钟固定 142.857 MHz，base overlay 本身就吃掉大部分时序余量；
  自研核在 7 ns 下估计 194.59 MHz，说明瓶颈在框架不在核。若要更大余量，得裁掉框架里用不到的
  MicroBlaze/音频/IO 子系统（会破坏 PYNQ `BaseOverlay` 的 API，暂不做）。

## 2026-10-18 / P3a 完成：板上逐位一致，PS/PL 对比 4.7×

**结果**
- 板上 `python3 sobel_dma.py` → **`COMPARE PASS (bit-exact)`**，0/2764800 个通道不一致；
- PL：659.1 ms/帧（1.516 fps、1.397 Mpixel/s）；
- PS（同板 ARM Cortex-A9 + numpy）：3108.4 ms/帧（0.320 fps、0.30 Mpixel/s）；
- **加速比 4.72×**，且两边输出逐像素完全一致（`golden_compare` 比对 0 不一致）。

**错误与纠正（第十九次～第二十一次）**

1. **有界核的 AXI-Lite 控制没接**。把 DMA 路线换成 `sobel_bounded`（ap_ctrl_hs）后重建，
   板上 `ol.ip_dict` 里只有 `axi_dma_0` 和 `ps7`——`sobel_0` 根本不在地址映射里。
   原因：`sc_ctrl` 只连了 DMA 的 `S_AXI_LITE`，核的 `s_axi_control` 悬空，
   `ap_start` 无处可写。修法：`sc_ctrl` 改成 `NUM_MI=2`，补一条 `M01_AXI → sobel_0/s_axi_control`。
   教训：**加带寄存器的 IP 时，"接上流"和"接上控制"是两件独立的事，漏掉后者不会报错，
   只会表现成"设备不存在"。**

2. **自由运行核在流结束时不排空流水线**。这是这次最花时间的根因：给 1280 拍输入，
   出来的不足 1280 拍，DMA 于是永远等不到 TLAST。判定方法是"传输结束差多少"——
   每次正好差 16 个字（一个 AXI burst），再配合"2560 拍传输在第 1280 拍被提前关闭"
   证明了 TLAST 生成器本身没问题，问题在核的输出拍数。

3. **板上跑任何脚本都要 sudo + venv 解释器**。PYNQ 3.1.1 的 Jupyter 以 root 运行，
   XRT 设备只有 root 能开；直接 `python3` 用的是 `/usr/bin/python3`（没有 pynq）。
   正确写法：`sudo env XILINX_XRT=/usr PATH=/usr/local/share/pynq-venv/bin:... /usr/local/share/pynq-venv/bin/python3 xxx.py`。

**人工判断**
- 接受"逐行 DMA"的 659 ms 作为**功能验证**数据，并在报告里明确标注它的开销主要来自
  720 次核启动 + 1440 次传输的软件开销，而不是算子；整帧传输列为下一步优化。
- 主机 numpy（40.7 ms/帧）比板上 PL 还快这件事，如实写进报告，避免"加速比"被误解。

## 2026-10-18 / 整帧 DMA：15.8 ms/帧，196.7×

**结果**
- 整帧一次传输：**15.8 ms/帧（63.45 fps、58.47 Mpixel/s）**，比逐行快 41 倍；
- 相对 PS numpy（3108.4 ms/帧）**196.7×**；
- 仍然 **bit-exact**（0/2764800 通道不一致）。

**错误与纠正（第二十二次～第二十三次）**

1. **DMA 长度寄存器只有 14 位**。整帧 3.6 MB 一传，运行时报
   `ValueError: Transfer size is 3686400 bytes, which exceeds the maximum DMA buffer size 16383`。
   `c_sg_length_width` 这个参数名听起来是 Scatter-Gather 专用，实际也决定简单模式的
   缓冲区长度寄存器宽度。改成 23 位（8 MB）后整帧传输才成立。
2. **TLAST 生成器在整帧模式下反而有害**。它按拍计数，在整帧传输里会在第 1280 拍
   提前"关闭"传输。既然有界核已经会把自己接收到的 TLAST 原样送出去，索性把它从块设计里去掉
   （RTL 保留在仓库里作为记录），并让核用 `line_width` 自己数行边界——
   这样无论软件怎么切分传输，核的行结构都不受影响。

**人工判断**
- 对比表同时保留"逐行 4.7×"和"整帧 196.7×"两档，并说明前者是软件开销、后者才是
  "算子 + DDR 带宽"的真实水平；只报最好看的数字会掩盖工程过程。
- 把 15.8 ms 与理论计算量（1280×720 在 100 MHz、II=1 下约 9.2 ms）对照写进报告，
  读者能看出还剩下多少优化空间（DDR 往返与启动开销约占 6.6 ms）。

## 2026-10-19（续二） / 延迟从"约一行"变成"16 个像素时钟"

**结果**
- 板上实测：**16 个像素时钟 = 160 ns @100 MHz**（720p60 的一行是 17.2 µs，即 <1% 行）；
- 实现方式：`axis_cycle_stamp` 在内核**前后各一个**，同一时钟同一复位，两个时间戳相减；
- 同轮还把输出与黄金模型的零容差比对保持住了（`reading` 15.6 ms/帧，0/2764800）。

**错误与纠正（第二十八次～第三十次）**

1. **戳内核的 AXI-Stream 引脚会让 TVALID/TREADY 脱离接口网**。第一版监视器用
   `connect_bd_net` 直接连 `enhance_0/s_in_TVALID` 等，Vivado 报
   `BD 41-759 ... tied-off to all 0's`，而且 impl 直接失败。改成"串在通路里的直通单元"才对
   （和自己写的 `axis_tlast_gen` 一个套路）。
2. **直通单元上"在飞像素数"恒为 0**。因为 `m_tvalid = s_tvalid`、`s_tready = m_tready`，

3. **单个直通单元的"首拍时间戳"也恒相等**。同一原因。必须在内核前后各放一个，才能得到内核延迟。

**人工判断**
- 三次返工都发生在"观测点位置"上，而不是算术上。教训记进坑表：
  **测延迟要在被测模块的两侧取样，不能在它旁边取样**。

### 37. 把"配置写进去了"当成"配置生效了"

**时间**：2026-10-22 凌晨

**我当时怎么想的**：GPIO 写入值与回读一致、BD 里九根线全部连到内核端口、
`enh_cfg_split.v` 的位映射和 PS 端打包完全一致、生成 RTL 里这些端口也确实参与运算
——四条都验证过，就断定"配置一定生效，可能是显示没刷新"。

**实际情况**：生成 RTL 里 `binarize`/`mono`/`invert`/`thresh`/`knee`/`split_x`
都被存进了 `*_read_reg_*` 寄存器，只在流水线 **prologue** 采一次；而内核是
`ap_ctrl_none` 自由运行的，prologue 只执行一次，所以这 6 个参数永远停在第一个值。
只有 `clarity`/`gain_lo`/`gain_hi` 是组合直连的，能实时改。
`pass → night` 那次画面变亮就是这 3 个实时参数在起作用。

**为什么没早点发现**：我一直在验证"信号有没有连上"，没验证"信号在运行期会不会被采样第二次"。
端口存在、连线正确、RTL 里引用了——这三件事都不等于"每个像素都重新读一次"。
判据应该是：**在生成的 RTL 里搜 `xxx_read_reg`**，有就是锁存。

**修正**：把这 6 个参数改成 BRAM 或 AXI-Lite 读，或者改配置后复位内核；
并在检查清单里加一条"自由运行内核的运行时配置，必须在 RTL 里确认没有 `_read_reg` 锁存"。

### 38. 修好了"配置不生效"，但代价是一次复位

**时间**：2026-10-22 晚

**改法**：加了 `enh_rst_gate`，用配置字空闲位 `cfg_hi[31]` 请求内核复位，
`write_preset` 里"先写参数、再断言复位、再释放"，让 prologue 用新值重新采样。

**验证**：采集卡上 4 张截图互不相同（原图 / 二值化 / 文档增强 / 高增益），
且每次切换后延迟仍稳定 21 拍。

**遗留**：每次换预设的当帧会花屏一帧（line buffer 被清空）。
彻底做法是把 6 个参数放进 BRAM（存储器读取无法被提到循环外），
但那要改 HLS + 重建 IP + 重建 overlay，属于优化项而不是阻塞项。

**记下来的一点**：先复位再写参数是错的——复位期间写入的旧值会被释放时的
prologue 采走。顺序必须是"参数就位 → 断言 → 释放"。这类时序细节只能靠
对照 RTL 的 prologue 行为来推，不能凭直觉。

### 39. 复位门控的两个后遗症：端口表缓存与异步释放

**时间**：2026-10-22

**第一个坑：Vivado 按模块名缓存 BD 的 module reference。**
我给 `enh_rst_gate` 加了时钟端口后重新综合，BD 里的 cell 仍然报
`the gate has no aclk pin`——即使删掉 cell 重新 `create_bd_cell -type module -reference`
也一样，因为缓存是按**模块名**索引的。换一个模块名（`enh_rst_bridge`）才拿到新端口表。
回头看，之前给 `axis_cycle_stamp` 加 `beats` 端口失败、最后放弃拍数计数，也是同一个原因
（当时误判成"Vivado 不支持"，绕过去了）。

**第二个坑：复位释放没有同步。**
第一版 `ap_rst_n = aresetn & ~cfg_hi[31]` 是纯组合的，而 `cfg_hi` 来自 100 MHz 的 PS 域、
内核跑在 142.857 MHz。用户在采集卡上看到的现象很关键：**不是换预设当帧花屏，
而是某些预设下持续闪烁**。这说明内核带着错乱的 line-buffer 指针退出复位，
而不是"抖一下就好"。

**修正**：改成标准的异步断言 / 同步释放复位桥：

```verilog
wire rst_n_async = aresetn & ~cfg_hi[31];
always @(posedge aclk or negedge rst_n_async)
    if (!rst_n_async) sync <= 2'b00;
    else              sync <= {sync[0], 1'b1};
assign ap_rst_n = sync[1];
```

**教训**：用户描述的现象必须逐字读。"花屏"和"闪烁"是两种不同的失效：
前者是瞬态、后者是状态异常。我一开始按"当帧花屏"解释，差点把它归到已知代价里不再查。
**跨时钟域的控制信号，即使只是"复位一下"，也必须做同步处理**；
而 BD 里的自定义模块一旦改端口，就要换模块名重建，不能指望刷新。

### 40. "闪烁"查了十几轮，最后靠读回帧缓冲破的局

**时间**：2026-10-22 晚

**我错在哪**：连续几轮都在"看现象猜原因"——猜黑帧、猜撕裂、猜缩放、猜复位相位。
每次改一版让用户看，用户看不清或说"还闪"，就再猜一个。这是低效的排查方式。

**破局点**：写了一个**不需要眼睛**的判据——把 VDMA 的 4 块帧缓冲用 numpy 读回来打印
`mean/min/max`。结果四块全是正常图像（`mean=131.5`），**"黑帧交替"当场被推翻**，
排查方向立刻从"缓冲内容"转到"输出核恢复"。

**真正的根因**：切预设要复位内核（第 37 条），复位截断 AXI-Stream，`v_axi4s_vid_out`

**修法**：复位后立刻 `stop/configure/start` 并重新填满帧缓冲，让输出链路

**教训**：能用代码读回来的量，优先读回来，不要靠人眼看。
诊断脚本的价值不在于"再试一次"，而在于**把假设变成可测的数字**。

### 41. 把"锁存的配置"搬进存储器：三次被 Vivado 缓存挡住

**时间**：2026-10-22 凌晨

目标很明确：切预设不再复位内核。做法是让内核每像素从存储器读一次配置，这样参数无法被
HLS 提成常量。

**第一课：常量下标会被折掉。** 写 `ap_uint<64> cfg[1]` 读 `cfg[0]`，HLS 证明下标是常量，
把数组变成普通输入端口，标志位照样被锁存（`binarize_reg_1458 <= cfg[40]`）。让下标依赖
运行期变量后，才生成真正的 BRAM 端口（`binarize_reg_1575 <= cfg_Dout_A[40]`）。

**第二课：小存储器会被推断成触发器。** `(* ram_style = "block" *) reg [63:0] mem [0:1]`
只有两项，Vivado 用触发器实现，于是 100 MHz 写、142.857 MHz 读变成被时序收敛的同步路径：
`WNS −1.393 ns，59 个失败端点`。用 `xpm_memory_tdpram` 显式例化才对（跨时钟在原子内部，
按字原子）→ `+0.289 ns`。

**第三课（最费时间）：三层缓存让 RTL 改动进不了网表。**
1. BD 的 module reference **按模块名缓存**（之前已记录）；
2. `create_bd_cell -type module` 会把模块**打包成 XCI**，之后改源文件完全无效；
3. `.gen` 下还缓存一份**已综合的 DCP**。
表现为：不管源码怎么改，失败路径始终是 `mem_reg[0][33] → dout_q_reg[33]`——这两个信号
只存在于旧版本。**用信号名当指纹**才确认网表没换。破法是删掉 cell、删掉打包目录与
`.gen` 缓存、重建。

**教训**：RTL 改了但结果没变时，不要怀疑综合设置，先用旧版本特有的信号名去网表里搜一遍。
命中就说明改动根本没进去。

### 42. 静默的悬空：引脚名大小写害我白跑两次构建

**时间**：2026-10-22 凌晨

新内核上板后画面全黑，`writeframe()` 永久阻塞。原因不是内核逻辑，而是**内核输出侧根本
没接上**：接线脚本按小写后缀查引脚（`s_out_tdata`），而 HLS 生成的是 `s_out_TDATA`，
`get_bd_pins -quiet` 把失败吞掉了。输入侧恰好拼对了，所以 BD 校验通过、位流照常生成。

**判据**：网络名等于引脚自身名字（`/enhance_cfg_0_s_out_TDATA`）就说明这个引脚悬空——
它没有和别的引脚共享网络。加上这条自动检查后，悬空会直接报错。

**另外两件事**：
- 首次 `writeframe` 偶发无限阻塞（采集卡还没锁定时序就没人消费）。给脚本加了看门狗 +
  重试：4 秒不返回就重启输出链路重试，三次失败才报错并提示检查采集卡。
- 板子的 FPGA manager 在一次异常退出后卡死，加载位流直接挂住（`timeout` 返回 124）。
  **重启板子**是恢复手段，之后一切正常。

**教训**：`-quiet` 用在查找上是危险默认值——它把"没找到"变成"没问题"。
凡是"连接/配置"这类操作，找不到就应当报错，并且用一条独立的断言把它证明出来。

### 43. "画面没了"其实是一条悬空的 HPD 线

**时间**：2026-10-22 下午

板子重启后演示只剩彩条。我的第一反应是查板子：时钟锁了、`writeframe` 11.5 ms、像素流在动
——**全都正常**。于是转到采集侧，才读出真正的状态：

```
hpd GPIO: ch1=0x00000000 tri1=0xffffffff
```

方向寄存器全 1 表示**两个通道都是输入**，也就是说这块板子从来没有驱动过输出 HPD；
历史上那些 `mmio.write(0x00, 0x1)` 全都写进了数据寄存器，而引脚仍是输入——**电气上没有
任何效果**。采集棒看不到 HPD，就关掉接收器显示自己的彩条。

**教训一**：写寄存器 ≠ 改变引脚。GPIO 要三步都确认：方向、数据、回读。
**教训二**：当板子侧的数字全都正常时，不要继续深挖板子，去读对端的握手信号。
这次我先在板子上多花了一小时，其实一条 `tri` 寄存器就能定案。

**顺带修掉的测量口径问题**：`axis_cycle_stamp` 只记录**第一个像素**的时间戳，所以读数带
几拍启动偏斜（跨轮 21/24/25 波动）。文档现在分开写：流水线深度 21 拍（HLS `Depth = 21`）
与片上单次测量 21–25 拍，不把两者混为一谈。

### 44. 目测是错的：一次被用户抓住的测量事故

**时间**：2026-10-22 晚

我看到几张截图里画面都向左偏、右侧回卷，就按预览像素数估算"偏移 30–40 像素且在变"，
据此判定是采集卡每次重锁的随机采样相位——**结论正好相反**。

用户一句"这和刚刚那批图片的偏移不是一样的吗"把我问住了。于是不再目测，写
`tools/diag/measure_capture_offset.py`：把每张截图缩放到参考卡片尺寸，**逐像素互相关**求最佳位移。
结果 43/45/46，**恒定**。而且这个值能和设计对上：内核 21–25 拍 + 时间戳/解包/FIFO ≈ 20 像素。

**教训**：能从数据算出来的量，永远不要用眼睛估。预览图上 20 个像素的差别在视觉上根本分不清，
但换算是 30 还是 45 会直接改变结论方向（"采集卡随机"还是"我们的设计固有"）。
另外，用户的质疑往往是对的——先验证，再解释。

**同一晚另一个发现**：每次重启进程后画面变彩条，不是处理链路的漏洞，而是
`VideoOut.configure()` 重新编程了像素时钟，TMDS 中断导致采集棒失锁。
`writeframe()` 依旧秒回、延迟计数依旧更新，因为断在时钟/串行化层。
修法是读回硬件模式，已匹配就只重启 VDMA 与时序发生器、不动时钟——**漏掉 `_hdmi.start()`
会让 VDMA 配好却无人消费**，这一点我也踩了一次。

### 45. 偏移不是常数：三次开机三个值，逼出了 SOF

**时间**：2026-10-22 深夜

我一直把水平偏移当成"固定值"，先测 43–46，再测 89，还用 `--roll` 去补。用户第三次截图时
我量出 **约 0 像素**——同一个位流、同一套脚本。三个值摆在一起，"固定偏移"的假设当场崩塌。

**重新推理**：什么机制会让相位每次开机不同？`v_axi4s_vid_out` 靠 SOF 对齐帧，SOF 走
TUSER；而我们的 TUSER 来自 VDMA 的 `m_axis_mm2s_tuser`，恒为 0。没有 SOF，输出核只能按
自己的时基自由跑——相位自然随机。

**验证线索**：Xilinx PG044 明确写 "SOF ... physically transmitted over the AXI4-Stream
TUSER0 signal, marks the first pixel of a video frame"；PYNQ 论坛对"自定义 HDMI 通路没画面"
的答复也是 "does not have all the necessary signals, tuser, tlast"。

**修法**：写 `axis_sof_gen`，用 TLAST + 行计数器造出缺失的 SOF，插在 pixel_unpack 与
vid_out 之间，组合直通不改延迟。

**教训**：当一个"常数"在不同会话里给出不同值，不要急着测得更准，先问"它凭什么应该是常数"。
我在这上面浪费了两轮 `--roll` 校准。

**附带**：`opt_design` 的 `[Opt 31-67] LUT4 ... missing a connection on input pin I3` 是
参数化比较（32 位常量 vs 9 位计数器）导致的，改成同宽度 `localparam` 即过。

### 46. 接口 vs 引脚：一个看起来能构建、实际加载不了的改动

**时间**：2026-10-23 凌晨

SOF 生成器的手写 RTL 版本构建成功了（WNS +0.241 ns），我原以为快成了。上板后 PYNQ 直接抛
`MetadataObjectNotFound`——**overlay 根本加载不了**。

根因是用**单引脚**把流接进/接出该模块，破坏了 `pixel_unpack` 与 `v_axi4s_vid_out` 之间的
**AXI4-Stream 接口**结构。hwh 里该核的输入叫 `video_in[port]`，一旦不再由接口驱动，
PYNQ 的元数据解析器就找不到 `s_axis_video_tdata`。

**教训**：在 PYNQ 设计里改流路径，必须是**接口对接口**。单引脚连接在 Vivado 里合法、
能综合、能出位流，但会在 PYNQ 这一层崩掉——而且是"加载失败"，不是"显示不对"，
排查方向完全不同。

**第二次尝试**改用 HLS 内核（`S_AXIS`/`M_AXIS` 真接口，II=1、228 MHz），思路正确，
但 BD 已经在第一次尝试里被改成了半迁移状态：引脚级网络残留、复位网络失去驱动。
`BD 41-1271 ... overridden by the user` 和 `NET <aresetn_1> has no source` 就是这个状态。
继续在脏 BD 上修补的代价已经超过重来，于是写了 `repair_bd.tcl` 恢复接口连接与复位，
综合验证通过，把 SOF 留作独立的、待集成成果。

**另一个教训**：BD 的每次"删除 + 重建"都可能带走相邻网络（复位网上只有两个引脚，
删掉一端就整条消失）。改 BD 之前应先把要保留的网络端点记下来。

### 47. 提亮看起来"更糟"：不是算法错，是增益通路在硬件里坏了

**时间**：2026-10-23 凌晨

用户上传了一张真实书页照片，说处理之后更难读。我第一反应是"预设没生效"，但截图里的
画面确实变亮了——只是布满规则竖条纹。

**逐层排除**（这一步做对了，没有猜）：
1. 纯色 64 输入 → `pass` 与 `clarity` 都是 std 0.08（完美均匀），**只有开增益**才 std 38；
2. 软件生成亮度 141 的纯色图 + `pass` → std 0.23，**排除显示/采集链路**；

碰运气。这次"纯色输入 + 单级开关"的两步就把范围从"整个链路"缩到了"一级乘法"。

**待办**：把配置改成每帧锁存一次（帧首读入寄存器，去掉逐像素 BRAM 读），重建内核后复测。

### 49. 全局拉伸的尽头是"光照平坦化"

**时间**：2026-10-23 凌晨

把 `page` 曲线做出来之后，我盯着对比图看了一会儿：左边（纯拉伸）顶部一片惨白、底部字发暗。
这不是参数没调好，而是**全局映射的物理极限**——一张光照不均的纸，任何"一条曲线"都只能把
一个亮度区间映射好。

正确做法是先把光照除掉：**亮度 ÷ 自身高斯模糊**（同态滤波的简化版），低频的光照被压平，
高频的笔画保留；然后再做分位拉伸，把纸面钉在固定亮度。

对比结果非常清楚：整页均匀、文字同等黑，强边缘从 11.6% 升到 14.7%。彩色照片会因此发灰，
所以默认只对"文档"使用，照片仍推荐 `bright`。

**方法上的收获**：先怀疑"参数不够好"，再怀疑"方法不对"。这次是后者——而判断依据是
**看一眼图**，不是再调一轮参数。

### 50. 一晚上三个负面结果，和一个真正的进展

**时间**：2026-10-23 凌晨

用户让我继续攻遗留问题。结果是：**一个真进展 + 三个负面结果**。

**真进展：SOF 进位流了。** 三次失败各有原因，逐一查清后终于通过：建在视频层级内、连接前清空
两端、`ap_rst_n` 必须显式接（悬空时内核一直复位，表现为 VDMA 不工作）、复位跨时钟域要豁免。
最终 WNS +0.206，流正常。

**负面结果一：锁存配置没修好条纹。** C 仿真通过、时序也修好了（+0.297），上板后条纹依旧。
**负面结果二：移位加法（绕开 DSP）也不行**——至少没能观察到改善，因为……
**负面结果三：观测通道坏了。** 这一轮里改配置不再改变屏幕，只有换图才变。也就是说画面在两次

是否不同）才确认它曾经冻结过。以后每次测量前先跑健康检查，是最便宜的一道保险。

**方法上的收获**：`ap_rst_n` 悬空的表现（VDMA 不消费）与"流路径断了"完全一样，但根因完全不同。
这次是靠**回读引脚网络**（而不是相信脚本打印的 "connected"）找到的。脚本说连上了，实际没有——
这类"脚本说谎"必须用回读来防。

**留给下一轮**：用 ILA 抓 `s_axis_video_tuser/tvalid/tready` 和 `vtg_vsync`，确认 SOF 断言时机，
同时确认流是否连续。有了波形，条纹和冻结两个问题应该能一起定位。

### 52. 一直找的"停流"，日志里早就写着

**时间**：2026-10-23 11:10

我把"画面凝固"当成一个神秘的硬件问题查了半宿。最后去读演示进程的**完整日志**（而不是只看状态
文件），第一行就是：

```
RuntimeError: DMA channel not started
```

**VDMA 的 MM2S 通道停了。** 于是：

- 屏幕冻在最后一帧 → 看起来"画面是好的"；
- 换图会刷新 → 因为推帧动作本身成功了（部分）；
- 改配置无反应 → 配置只作用于新流动的像素，而流早就停了。

我今晚至少有五次"配置不生效"的结论，全部是这个假象的产物。

**教训**：`/tmp/hdmi_state.txt` 只记录"我以为在显示什么"，**进程的 stderr 才记录"实际发生了什么"**。
调试一个长时间运行的进程，先看它的异常，不要只读它写的状态文件。

**已加防护**：捕获该异常并重启 VDMA 通道，失败计数入状态，进程不再死。
**未解**：通道为什么停。SOF 位流更容易触发，怀疑视频核等 SOF 时把流憋停导致欠载。

### 55. 两个"硬件缺陷"都是我自己造成的

**时间**：2026-10-23 13:05

最后把内核退回最初那版、保留 SOF，重新构建。结果：

也就是说，**"增益条纹"和"增益无效"这两个我查了半宿、试了三种改法的"硬件缺陷"，都不是设计问题**：

- **条纹**来自"两个演示进程用不同参数交替写同一份配置字"。每像素从 BRAM 读参数，
  帧内参数不稳定就变成列周期条纹。单实例下完全复现不出来。
- **增益无效**是 latch+II=2 那一版内核的回归（`clarity`/`binarize` 有效、增益无效）。

我为这两个"缺陷"改过 HLS 内核、做过三次构建、写过两份分析文档。真正的修复是**一个 flock** 和
**一次 git checkout**。

**这次的教训比技术细节重要**：我反复在"被测对象"里找原因，却没有先确认"测量环境"是否干净。
今晚所有结论的可靠性，都建立在"板子上只有一个进程、部署的文件是完整的"这两个前提上，
而这两个前提我一次都没验证过。

以后排查异常，第一步固定为：
1. `ps` 确认只有一个演示进程；
2. 核对板上 `.bit`/`.hwh` 的 MD5 与仓库一致；
3. 换两张截然不同的图确认画面真的在更新。

这三步花不了一分钟，今晚能省下五个小时。

### 56. 指标选错，结论就会反

**时间**：2026-10-23 11:30

验证"暗图处理后是否更清楚"时，我先用了"全幅边缘能量"：2.73 → 4.35，看着是大幅改善。
但截图一看，纸面发白、字反而模糊。原因很简单——**整体提亮会让所有梯度都变大**，
边缘能量跟着涨，它衡量的是亮度而不是可读性。

换成**局部对比度**（5×5 窗口标准差的分位p90）：20.12 → 37.81（+88%），水平边缘 2.16 → 3.46。
这次和肉眼观感一致：字确实更清楚了，只是纸底接近白色。

同一件事，两个指标一个说"变亮"，一个说"变清楚"。**选指标时要想清楚它衡量的是什么**，
尤其是当"被测量的量"和"想要的改善"不是同一个东西时。

顺带修了一个小毛病：`show_image.ps1` 加 `-NoTone`。原本想用 `-Tone ''` 表示"不处理"，
但 PowerShell 会把空串吞掉并报"缺少参数"——这种"参数看起来给了其实没给"的坑今晚已经踩过好几次。

### 57. 用户说"视频还没验证"，结果它从来没工作过

**时间**：2026-10-23 14:10

用户要的是"上传视频 → 自动选最清晰挡位 → 整段连贯"。我先去接自动选挡，接完测试发现
`play_preset` 永远为空。一路查下去，日志里躺着：

```
NameError: name 'play_buf' is not defined
```

`play_buf` 和 `play_cache` 在**任何提交里都没有定义**。播放循环每帧抛异常，被 `except` 吞掉，
只留一行 "play write failed"。也就是说——**视频播放从来没有真正工作过**，我之前看到
`playing=24 frames at 12 fps` 就以为它在播，其实那只是横幅文字，屏幕上一直是静止帧。

这是本晚第二次栽在同一个坑里：**"日志说在播"不等于"画面在动"**。上次是 VDMA 停机，这次是
异常被吞。两次的教训合起来就是：判断某件事是否真的发生，必须看**外部可观察的结果**（画面变化），
而不是程序自己打的横幅。

修掉 `play_buf/play_cache` 后帧率仍然只有 5 fps，计时日志显示每帧只要 6 ms——问题在别处：
播放分支每 15 帧会落到主循环末尾的 `time.sleep(args.tick)`（2 秒），正好对应日志里的
`behind by 1920 ms`。改成播放时 50 ms 短休眠，立刻 **24.0 fps、0 卡顿**。

第三个 bug 是 `/tmp` 的 sticky 位让 `-Stop` 的 `rm -f` 静默失败——删除改截断。

**自动选挡本身反而最顺利**：离线分析可以把"未来帧"纳入平滑窗口，所以不需要迟滞，也就没有迟滞
带来的延迟；再用"帧间亮度跳变最大"把边界吸附回真实切点，实测 24 帧片子给出 2 段、
边界正好落在第 12 帧。
