## 四、作品简介 · 详细版（超上限，留给展板、报告摘要、答辩材料）

```
低照度条件下的图像观察（夜间巡检、暗光取证、车载夜视、工业与显微成像）真正的瓶颈往往不是帧率，而是延迟：通用手机或 PC 方案从采集到显示通常有 100~300 ms，移动观察时画面迟滞、拖影，长时间使用容易疲劳。

本作品在 PYNQ-Z2（Zynq-7000 XC7Z020）上把整条增强链放进像素流里，而不是放在帧缓冲之后：局部对比（clarity）→ 两段色调曲线（knee + gain_lo/gain_hi）→ 二值/反色/单色（thresh/binarize/invert/mono）→ 左右分屏（split_x），全部由一颗 AXI-Stream 流式内核逐像素完成，内核不访问 DDR、链内不落帧缓存，像素进多少出多少。片上双时间戳实测流水线延迟 16 拍 = 160 ns（HDMI 通路 21 拍 = 147 ns），160 ns 约等于 720p60 一行时间（17.2 µs）的 1%，处理延迟的量级是「一行的百分之一」，不再是「一帧」。

核心算子 enhance 由 Vitis HLS 2026.1 实现：II=1，BRAM 3 / DSP 2 / FF 2168 / LUT 1659（3%），7 ns 约束下估计 Fmax 194.59 MHz，高于视频通路的 142.857 MHz。59 bit 参数经 AXI GPIO 写入 cfg_bram（XPM 真双口），内核每像素读一次，因此切预设退化成一次寄存器写：不复位、不中断像素流，实测 150 s / 25 次切换 / 741 次写帧，0 次超过 60 ms 的卡顿。

为回答「结果对不对」，全链采用整数定点实现，并配有独立编写的 numpy 黄金模型：AXI-DMA 整帧回环比对下，8 档 DMA 参数表各 0/2764800 通道不一致（逐位一致），720p 整帧 15.6 ms（63 fps）；同一个内核又在 HDMI 通路以 640×480@60 持续出图（交付位流 WNS +0.206 ns），既能被数字验证，也能被肉眼检验。算子族另含 Sobel、高斯、锐化三个流式卷积核：以 Sobel 为例，同一算法 PS 纯软件 3108.4 ms/帧（0.32 fps），PL 15.8 ms/帧（63.45 fps），加速 196.7 倍。

**边界**：帧源是 PS 预载的图像与视频帧，经 DDR → VDMA 送进像素通路。本板 HDMI 输出实测只支持 640×480（原厂位流同样如此），而 HDMI 输入 IP 无法工作在 640×480，所以「摄像头 → 板子 → 显示器」的直通链路没有打通，端到端延迟与功耗都没测。交付形态是：内核位于真实像素流中、PS 只送帧与改配置、板上 60 Hz 持续输出。构建全流程（HLS 工程、块设计、位流、上板测试、图片与视频上传演示）均已脚本化，可从零一条命令重建。
```

## 六、提交前自检

1. `python tools/check_consistency.py --strict`——仓库里"实时 / 端到端一行 / 旧 WNS / 旧档数 / 偏移读数"这些旧说法会被这条门禁挡下来。
2. 简介里出现的每个数字都要能在 `docs/facts.md` 找到同一数值；找不到就删掉那句话，不要现场解释。
3. **「帧缓冲」只能挂在增强链上，不能挂在整条链路上**。交付形态是「PS 预载帧 → DDR → VDMA → 内核」，DDR 里那一步本身就是帧缓冲，所以写「帧源经 VDMA 送入，不经过帧缓冲」会自相矛盾（仓库口径见 `docs/video_demo.md` §七）。正确说法：「PL 内的增强链不经帧缓冲」「链内不落帧缓存」。
4. **196.7× 前面要有「以 Sobel 为例」**，否则会被读成 enhance 的加速比（`docs/facts.md` §6）。
5. **160 ns 要能看出是哪条通路**：DMA 通路双时间戳测的是 16 拍 = 160 ns，HDMI 通路是 21 拍 = 147 ns，两个数都对但别混用。
6. 字数按「字符数（不含空格，含标点与英文数字）」核对：提交版 414，离 500 上限还有 86。
