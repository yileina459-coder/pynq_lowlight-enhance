# 校赛一页材料：低延迟视觉增强终端

> 参赛方向：2026 全国大学生嵌入式芯片与系统设计竞赛 · FPGA 创新设计赛道 · AMD 自主选题
> 平台：PYNQ-Z2（XC7Z020）　工具：Vivado / Vitis HLS 2026.1
> 状态：**已上板**——HDMI 通路 640×480@60 持续出图、处理延迟 21 拍、10 档运行期切换；
> DMA 通路 8 档逐位一致（各 0/2764800）。完整口径见 `docs/facts.md`。

## 一句话

一台**不经过帧缓冲**的低延迟图像增强终端：增强链在 PL 的像素流中逐像素完成，
处理延迟 **21 个像素时钟 = 147 ns**（约 720p60 一行的 1%）。帧源由 PS 预载、VDMA 送入；
本板 HDMI 输出只支持 640×480、输入不支持该模式，摄像头直通受硬件限制未打通。

## 1 问题与用户

- 用户：需要在夜间/弱光下判读画面的使用者（安防巡检、取证、车载夜视、工业与显微成像）
- 痛点：通用手机/PC 方案从采集到显示通常 100~300 ms，**延迟大导致画面迟滞、拖影与疲劳**
- 关键判断：这类设备的核心指标不是帧率，而是**延迟**；本作品测到的是 PL 内部处理延迟，
  端到端（含采集与显示）受本板 HDMI 限制尚未测

## 2 方案

```text
PS 预载图像/视频 → DDR → VDMA MM2S → stamp_in → enhance → stamp_out
                 → pixel_unpack → sof_gen → v_axi4s_vid_out → rgb2dvi → HDMI OUT
```

- **零帧缓存**：像素边走边算，处理延迟 21 拍（147 ns），而不是一帧
- **参数化**：59 bit 配置（清晰度/拐点/双段增益/阈值/反色/单色/分屏位置）由 PS 运行期下发，
  配置驻留双口 BRAM、内核逐像素读取；内置 **10 档场景预设**
- **分屏对比**在核内用现成的列计数器实现，零额外资源
- 整数全定点，硬件与 numpy 参考模型**逐位一致**（8 档验证参数表），可做 0 容差回归

## 3 已完成的证据

| 项目 | 方法 | 结果 | 证据 |
|---|---|---|---|
| 逐位正确性 | 独立编写的 C++ 黄金模型，两种配置（对比度+分屏 / 色调+二值+反色+单色） | **各 9216 拍 0 误差** | `src/hls/enhance/tb_enhance.cpp` |
| **板上逐位一致** | AXI-DMA 整帧回环，8 档参数表逐一与 numpy 比对 | **各 0/2764800 通道**，15.6 ms/帧 | `board/enhance_dma/` |
| 独立复核 | numpy 黄金模型，恒等预设必须逐位等于输入 | **通过** | `sim/enhance/golden_enhance.py` |
| 综合结果 | Vitis HLS 2026.1，`xc7z020clg400-1`，7 ns 约束 | **II=1**；BRAM 3 / DSP 2 / FF 2168 / LUT 1659（3%）；估计 **Fmax 194.59 MHz** | `build/hls/enhance/` |
| 视觉验证（板上） | 暗页在 4 个预设下的平均亮度 | `pass` 29 → `bright` 96 → `document` 100 → `night` 104 | `board/hdmi_stream_enhance/evidence/presets/` |
| 既有硬件证据 | DMA 通路整帧传输、与黄金参考比对（Sobel 算子族） | **0/2764800 通道不一致**；15.8 ms/帧；相对 PS 196.7× | `board/dma_sobel/` |
| 真机 HDMI | 采集卡 640×480；HLS `Depth = 21`；预设运行期切换 | **21 拍**、**10 档**、741 次写帧 0 卡顿 | `board/hdmi_stream_enhance/` |
| 时序 | 交付位流实现报告 | **WNS +0.206 ns @142.857 MHz**，0 失败端点 | `timing_impl.rpt` |
| 画面偏移 | 八色带 + 互相关，启动后标定 | 本次 216.8 px → `roll=218`，残差 **0–1 px** | `docs/output_offset.md` |

时钟预算：视频通路 142.86 MHz，核估计 194.59 MHz，余量约 27%。

## 4 关键指标

| 指标 | 目标 | 现状 |
|---|---|---|
| 流水线延迟 | < 1 行（约 17 µs @720p60） | **DMA 16 拍 = 160 ns**；**HDMI 21 拍 = 147 ns** |
| 端到端延迟 | < 50 ms（不眩晕阈值） | **未测**：直通受本板 HDMI 限制（见 `docs/hdmi_status.md`） |
| 吞吐 | 720p 整帧 | **15.6 ms/帧 = 63 fps**（DMA）；HDMI 640×480@60 持续出图 |
| 资源 | < 5% LUT | 3% |
| 功耗 | 待 USB 功率计实测 | 未测（无板载功率计，不写估算值） |
| 与手机方案对比 | 同一把尺子（毫秒表 + 高帧率拍摄） | 未测 |

### 4.1 真机 HDMI 结果（采集卡实测）

| 项目 | 结果 |
| --- | --- |
| HDMI 输出（板子上限） | 640×480 @60（800×600/720p/1080p 一帧都不消费，原厂位流同样如此） |
| 内核在像素通路上 | ✅ 延迟 **21 个像素时钟 = 147 ns** |
| 预设运行期切换 | ✅ **10 档**；150 s / 25 次切换 / 741 次写帧，0 次卡顿 |
| 8 档逐位一致性 | ✅ DMA 通路各 **0/2764800** 通道不一致（验证参数表） |
| 画面偏移 | ✅ 每次启动标定（本次 218），残差 0–1 px |
| 仍受限 | HDMI **直通**不可行（输出只能 640×480，输入 IP 不支持该模式）；偏移未在位流层根治 |

**答辩要点**：同一份内核既跑 DMA 通路（逐位可证）又跑 HDMI 通路（肉眼可看），
两条通路的延迟与正确性都有实测数据；HDMI 的两次"看似失败"最终都定位到
可解释的硬件/工具行为（输出上限、HLS prologue 锁存），而不是含糊的"没调通"。

## 5 与替代方案的区别

| 方案 | 延迟 | 功耗 | 现场可重构 | 可验证性 |
|---|---|---|---|---|
| 手机 App / PC + OpenCV | 100~300 ms | 数瓦 | 否 | 依赖库版本 |
| GPU 边缘盒子 | 30~100 ms | 10 W+ | 否 | 难 |
| **本作品（PL 流式，VDMA 供帧）** | **PL 处理延迟 21 拍 = 147 ns**；端到端未测 | 未测 | **是（寄存器级）** | **逐位一致（8 档表）** |

## 6 风险与计划

| 风险 | 应对 |
|---|---|
| 偏移随像素流重启变化 | 已做成启动后自动标定；视频上传不再清零（`-Roll` 默认保留） |
| 采集棒丢锁后不能自恢复 | 演示只启动一次，参数走 `/tmp/hdmi_*.txt`；掉锁就拔插 HDMI 线/重启板子 |
| 时序余量只有 +0.206 ns | 保持交付位流不再加逻辑；三路算子并行未接入 |
| 时间（距提交 11/04 仅两周） | 11/01 设止损线，回退可交付版本 |
