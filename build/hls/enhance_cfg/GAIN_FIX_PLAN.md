# 增益缺陷修复方案（待构建验证）

## 已确认的事实
- 纯色输入 + gain_lo=56 → 屏上出现周期约 3 像素的竖条纹（std 38），逐行相同；
- clarity（gain=16）与 pass 完全干净（std 0.08）；
- 条纹幅度随增益线性增长（16→0.23, 17→2.97, 24→21.98, 32→20.06）；
- CSIM 对同样的配置输出均匀（64×2 = 128），所以 C 模型正确，问题在实机。

## 第一次修复尝试（已做，失败）
把配置从“逐像素读 BRAM”改成“每行首像素锁存到寄存器”。
- CSIM 通过（新写的 tb_enhance_cfg 检查了均匀性、换配置生效、恒等直通、TLAST/TUSER）；
- 综合通过（II=1，194.59 MHz）；
- **实现失败：WNS −2.117 ns，128 个失败端点**（原设计 +0.289）。

推测：锁存后 HLS 把配置寄存器并入了像素数据通路，组合路径变长。

## 下一步（本文件对应的方案）
给流水线两个时钟周期：#pragma HLS PIPELINE II = 2。
- 吞吐 71.4 Mpixel/s，而 640×480@60 只需 18.4 Mpixel/s，**仍有 3.9 倍余量**；
- 延迟从 21 提高到约 42 拍（0.29 µs），对显示无影响；
- 给原本 −2.117 ns 的路径两倍时间，理论上有充足余量。

改法：src/hls/enhance/enhance.cpp 里 enhance_stream_cfg 的 pragma 改为 II=2
（端口版 enhance_stream 保持不变），然后 HLS → refresh_enhance_ip.tcl → build。

验证：纯色 64 + gain 24 → 屏幕应当**完全均匀**（std < 2）。
若仍条纹，则问题不在配置读取，需用硬编码增益的版本做对照实验（编译期常量，不读 BRAM）。
