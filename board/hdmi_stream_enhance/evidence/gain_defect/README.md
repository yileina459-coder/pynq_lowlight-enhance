# 这份"增益缺陷"证据的结论：不成立

这里的图片（`stripes_gain_1p5x.png` 等）记录了 2026-10-22 夜里的现象：纯色输入、`gain_lo=56`
时，输出出现周期约 3 像素的竖条纹，且每一行完全相同。

**2026-10-23 复核后的结论：这不是设计缺陷。**

## 原因

当时板子上不止一个演示进程在跑（`kill_hdmi_demos.sh` 的模式列表漏了 `hdmi_resident`）。
两个进程各自打开同一份 overlay、各自往同一个 AXI GPIO 写配置字。内核按像素从 BRAM 读配置
（这是为了让预设切换不停流而做的设计），于是同一帧内不同像素可能读到不同版本参数，
表现出来就是**列周期条纹**——而每一行相同，正说明它是按列生成、与行无关。

## 复核数据（单实例，同一份内核）

| 增益 | 平均亮度 | 列 std | 判定 |
|---|---|---|---|
| 1.00× | 230.5 | 1.11 | 均匀 |
| 1.25× | 249.8 | 3.14 | 均匀（接近饱和） |
| 1.50× | 250.2 | 2.47 | 均匀（饱和） |
| 2.00× | 250.2 | 2.47 | 均匀（饱和） |

连续 15 分钟运行，0 次 `writeframe` 失败。

## 现在的防呆

- `hdmi_resident.py` 用 `fcntl.flock` 保证单实例，第二个进程直接退出；
- `tools/board/kill_hdmi_demos.sh` 的模式列表包含 `hdmi_resident`，并在结尾核对剩余数量，
  有残留就返回非零。

## 留作教训

这些图片保留在仓库里，但它们说明的是**测量环境不干净**，而不是硬件有缺陷。最初的分析文档
（三种修复尝试：每行锁存 / II=2 / 移位加法）同样基于这个错误前提，其中"每行锁存"确实修好了
时序（+0.297）却没修好条纹——因为条纹本来就不在配置读取的稳定性上。
