# 视频播放与自动挡位选择

上传一段视频，程序分析它、选出合适挡位，然后在板上实时处理播放——整个过程不重启演示进程。

## 图形界面（推荐，不需要命令行）

双击仓库根目录的 **上传视频.bat**：选视频、选播放方式、点「开始播放」。
把视频文件拖到该图标上，会直接带着路径打开窗口。
窗口里还会显示分析结果（整段最高分、每段的帧范围与挡位），因为自动选了什么应该看得见。

## 命令行用法

```powershell
# 整段一个挡位（最稳，推荐先试这个）
tools\board\play_video.ps1 -Video 我的视频.mp4 -Auto clip

# 按场景切换挡位（只在真正的场景切换处换，不会闪）
tools\board\play_video.ps1 -Video 我的视频.mp4 -Auto adaptive

# 自己指定挡位（不分析）
tools\board\play_video.ps1 -Video 我的视频.mp4 -Preset bright

# 停止播放，回到静态图片
tools\board\play_video.ps1 -Video x -Stop
```

## 两种自动模式的差别

| 模式 | 做法 | 何时用 |
|---|---|---|
| `clip` | 对每一帧算所有候选挡位的可读性分数，取**平均分最高**的那个，整段用它 | 追求绝对稳定；画面里没有剧烈的明暗变化 |
| `adaptive` | 逐帧选，再用**对称窗口平滑 + 边界吸附**压成少数几段 | 一段视频里有明显不同的场景（暗讲座 + 亮白板） |

`adaptive` 的规则只有两条，都是为了"不闪"且"不漏场景"：

1. **逐帧取最优，再合并过短段**：任何短于阈值的段都并入相邻段——那么短的段是评分抖动而非决策，
   逐帧抖动的 A/B 噪声正是这个形状，会自己塌缩掉。
   阈值按**时长**换算（默认 0.25 秒 × fps），因为"10 帧"在 4 fps 下是 2.5 秒（挡住真场景），
   在 30 fps 下只有 0.33 秒（挡不住抖动）。
2. **边界吸附**：评分在切点附近会偏移一两帧，所以在窗口内找"帧间平均亮度跳变最大"的位置，
   把边界挪回真正的切点。

早期版本用过"对称窗口平均"，但它会把**短场景抹平**：一段 8 帧的亮场被前后 24 帧暗场平均掉，
整段塌成一个挡位。合并规则已经解决了窗口本来要解决的问题，所以窗口被移除了。

候选挡位只取**观感相容**的一族：`pass / clarity / bright / night / document / reading`。
`invert`、`binarize`、`split` 属于风格化效果，绝不自动选择——一段视频中间突然反相六帧，无论
分数多高都不能看。

评分用 `tools/score_capture.legibility`：把平均亮度拉向 130、对过曝扣分，所以"整幅提亮"不会赢。

## 板上如何实时切换

播放循环在推每一帧之前，按排程调用 `hl.write_preset()`。配置走 BRAM，**切换不中断像素流**
（实测 741 帧 / 25 次切换 / 0 次卡顿）。排程文件会被**逐帧热加载**，所以播放中重新分析也能立刻生效。

排程与手动预设分开记录：`/tmp/hdmi_state.txt` 里 `preset=` 是操作者的选择，`play_preset=` 是
排程当前要求的挡位；停止播放后会自动恢复手动预设。

## 实测结果

测试片段：24 帧，前 12 帧暗底、后 12 帧亮底，方块持续移动（`scene_clip.gif`）。

| 项目 | 结果 |
|---|---|
| `-Auto adaptive` 的分析结果 | 2 段：帧 0–11 `night`，帧 12–23 `clarity`，**边界正好在真实切点** |
| 播放帧率 | 请求 24 fps，实测 **24.0 fps**，**0 次卡顿** |
| 切换日志 | `preset -> night (frame 0)`、`preset -> clarity (frame 12)`，每 24 帧循环一次 |
| `-Auto clip` | `play_preset=document`（平均分最高），全程不变 |
| 单帧成本 | 解码 0.0 ms + 拷贝 3.4 ms + 写帧 3.4 ms（缓存命中后） |

## 修掉的三个真 bug

1. **`play_buf` / `play_cache` 从未定义**。播放循环每帧抛 `NameError`，被 `except` 吞掉，只在日志
   里留一行 "play write failed"。git 历史里任何提交都没有这两个定义——也就是说**视频播放从来就没
   真正工作过**，之前看到的 `playing=24 frames at 12 fps` 只是横幅文字。
2. **每 15 帧卡 2 秒**。播放分支每 15 帧会落到主循环末尾的 `time.sleep(args.tick)`（2 秒），日志
   表现为 `behind by 1920 ms`，实测帧率被压到 5 fps 以下。改为播放时用 50 ms 短休眠。
3. **`-Stop` 一直无效**。`/tmp` 有 sticky 位，普通用户删不掉 root 创建的 `/tmp/hdmi_play.txt`，
   `rm -f` 静默失败。改为截断文件（0666 可写）。

## 视频格式

- **MP4 / MOV / MKV**：需要 ffmpeg。本机已放在 `.tmp\tools\ffmpeg.exe`（`tools/make_video_frames.py`
  会按 PATH → `.tmp\tools` → `tools\bin` 的顺序查找）；换机器时
  `winget install Gyan.FFmpeg` 或把 `ffmpeg.exe` 放到 `.tmp\tools\` 即可。
- **GIF / 动态 WebP**：不需要 ffmpeg，走 Pillow 回退。
- 找不到 ffmpeg 时会打印明确提示（缺什么、怎么装），不会只说"出错了"。

## 已知限制

- 帧存在板上 DDR：每帧 0.9 MB，`-Seconds` 默认 6 秒，30 fps 约 166 MB。
- 分析是**离线**的：先在 PC 上算完再播。真正的"边解码边实时选挡"需要板上做统计，代价会大得多，
  而离线分析已经能做到逐帧最优，所以没走那条路。

| 切换 | `preset -> clarity (frame 12)` / `preset -> reading (frame 0)`，每循环一次 |
