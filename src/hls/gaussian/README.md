# gaussian — 流式 3×3 高斯模糊核

## 是什么

把 32/24 位 RGB 像素流做 3×3 高斯模糊（1-2-1 可分离核）：

```text
   1 2 1
   2 4 2     总和 16 → 输出 = 加权和 >> 4
   1 2 1
```

与 Sobel 核共用同一套窗口结构（三个轮转行缓冲 + 每行 3 抽头移位寄存器），
所以同样是 **II=1、每时钟 1 像素**。

## 接口与边界策略

- 接口与 Sobel 完全一致：AXI4-Stream 32 位（低 24 位为 RGB），`TLAST` 为行尾，
  侧带信号透传，`ap_ctrl_none` 自由运行；
- 边界策略也与 Sobel 一致（水平复制、垂直用行缓冲里的上一帧行），
  因此两者可以共用同一套黄金参考工具。

## 已验证结果（2026.1，`xc7z020clg400-1`，7 ns 约束）

| 项目 | 结果 |
| --- | --- |
| C 仿真 | `GAUSSIAN TB PASS`，9216 拍，三帧预热后逐像素 0 误差 |
| 吞吐 | II = 1，循环深度 8 |
| 时序 | 估计 Fmax **194.59 MHz**（视频时钟 142.86 MHz，余量充足） |
| 资源 | BRAM 9（3%）、LUT 986、FF 1021、DSP 0 |

BRAM 比 Sobel 多，因为行缓冲存的是 24 位彩色而不是 8 位亮度。

## 一个真实的坑（已修复）

第一版用"先行后列"两遍实现：先算 `h = left + 2*mid + right`，再算
`h_top + 2*h_mid + h_bot`。中间结果最大 `4*255 = 1020`，需要 10 位，
但第一版把它塞回 24 位像素的 8 位字段里，**静默截断**——仿真里绿通道读回 31 而不是 175。

修复方式：改成一次 9 抽头求和、用 12 位累加器（最大 `16*255 = 4080`），最后统一 `>>4`。
这个 bug 只有靠逐位比对才会暴露，靠肉眼"看着像模糊了"是发现不了的。
